# Technical reference

For developers working on this codebase. Written in English; everything the
site's owner reads is Dutch.

This document describes how the pieces fit together, and why each piece is the
way it is. Where a decision is load-bearing — a security boundary, a constraint
that came from outside — the reasoning is given rather than assumed, because
that is what stops it being undone by accident.

## 1. Stack

Laravel 13.24 · PHP 8.4 · Inertia v3 · React 19 · TypeScript · Tailwind 4 ·
shadcn/ui · PostgreSQL 17.

Scaffolded from `laravel/react-starter-kit`. Authentication is **Fortify**;
typed route helpers come from **Wayfinder** (`@/routes`, `@/actions`,
regenerated by `php artisan wayfinder:generate --with-form`).

Tests are PHPUnit against real PostgreSQL, and **Playwright** against real
nginx for the things only a browser can see — see §14.

There is no Redis, no queue worker, no object storage and no Elasticsearch.
That is a decision, not an omission. Adding infrastructure is an architectural
change, not a performance tweak.

## 2. Container topology

`compose.yaml` is production; `compose.dev.yaml` overlays development.

| Service | Image target | Role |
|---|---|---|
| `app` | `production` / `development` | PHP-FPM |
| `web` | `web` | nginx, publishes `127.0.0.1:8080:80` |
| `database` | `postgres:17-alpine` | PostgreSQL |
| `vite` | `development` | Vite dev server (dev only) |
| `tunnel` | `cloudflare/cloudflared` | behind the `tunnel` profile |

Volumes: `database`, `media` (private uploads, shared read-only with nginx),
`logs`, and a bind mount `./storage-import` for `media:import`.

**nginx + PHP-FPM rather than FrankenPHP** because gated media is streamed by
nginx via `X-Accel-Redirect` — see [§7](#7-media-storage-upload-serving).

`docker/php/entrypoint.sh` runs on every boot and must stay idempotent. It
waits for a real database connection, migrates, seeds the admin from `ADMIN_*`
if configured, runs `db:seed` (education levels; the seeder no-ops once any
level exists), prunes abandoned upload chunks, and builds or clears the config,
route and view caches depending on `APP_ENV`.

> The entrypoint is baked into the image. Editing it and running `restart`
> changes nothing — rebuild.

`docker/nginx/app.conf` is an nginx **template**, not a finished config: the
image copies it to `/etc/nginx/templates/default.conf.template` and the
official entrypoint runs `envsubst` over it at boot. Exactly two things are
substituted, `CSP_DEV_SRC` and `CSP_DEV_CONNECT`, and both default to empty in
the image so the file is correct with no environment at all;
`compose.dev.yaml` fills in the Vite dev server's origin.

That indirection exists because a CSP origin is resolved by the *visitor's*
browser. `http://localhost:5173` written into the shipped policy does not name
the deploy machine, it names the student's own, so the site was telling every
browser that scripts and styles from whatever was listening on their loopback
were permitted. One file still has to serve both stacks — the development
stack bind-mounts this exact path, and a second file that failed to mount
would stop nginx from starting — so a variable is the only way to say
"development only" here.

`NGINX_ENVSUBST_FILTER` is set to `^CSP_` in the image and must stay set:
`envsubst` substitutes `$VAR` as well as `${VAR}`, so without the filter any
environment variable sharing a name with an nginx variable would take `$uri`,
`$request_uri` or `$document_root` out of the config. For the same reason the
comments in that file name the two variables without a `$`.

`SecurityHeaderTest` pins all of this: that no policy names a development
origin, that the config is installed as a template in both stacks, and that
every location setting a header of its own repeats the whole set.

## 3. Development

```bash
docker compose -f compose.yaml -f compose.dev.yaml up -d
```

| Task | Command (prefix `docker compose -f compose.yaml -f compose.dev.yaml`) |
|---|---|
| Logs | `logs -f app` |
| Artisan | `exec app php artisan <cmd>` |
| Tests | `exec app php artisan test` |
| Format PHP | `exec app ./vendor/bin/pint` |
| Types | `exec vite npm run types:check` |
| Lint | `exec vite npm run lint` |
| Production build | `exec vite npm run build` |

Site `http://localhost:8080` · Vite `5173` · PostgreSQL `127.0.0.1:55432`
(not 5432; Windows reserves parts of that range).

**Vite runs on the application image, not `node:alpine`** — the Wayfinder
plugin shells out to `php artisan`, so the container needs PHP and `vendor/`.

`vite.config.ts` must set both `server.origin` and `server.cors`. Without
`origin`, `laravel-vite-plugin` writes the container's bind address into
`public/hot` and the browser tries to fetch `http://0.0.0.0:5173/…`. Setting
`origin` alone narrows the plugin's CORS allow-list to itself. After editing
that file, **restart** the `vite` service; a reload is not enough.

## 4. Domain model

```
Topic (self-referencing, depth 0–2)
 ├── Topic
 │    └── Topic
 └── Page  ← attaches at any depth
```

| Table | Notes |
|---|---|
| `topics` | `parent_id`, `depth` (0–2), slug, icon, `content` jsonb, `sort_order`, `is_hidden`, `access_password_id?` |
| `pages` | `topic_id`, `hero_image_id?`, `content` jsonb, `content_text`, `access_password_id?`, `search_vector` |
| `settings` | `key` (PK) → `value` jsonb. Overrides only; defaults live in PHP |
| `access_passwords` | `name`, `password_hash` (not fillable, `$hidden`) |
| `education_levels` | Seeded, never hardcoded |
| `images` | `alt_text` NOT NULL + DB CHECK |
| `media_files` | `kind` ∈ {`document`, `video`} |
| `page_downloads` | + `education_level_page_download` pivot, `downloads_count` |
| `page_media_references` | Derived; rebuilt wholesale on every body save |
| `slug_redirects` | Old full path → polymorphic target |
| `media_uploads` | Chunk staging for in-flight uploads |

**Depth and cross-table sibling-slug uniqueness are enforced by PostgreSQL
triggers**, not only in PHP — see the long comment in
`2026_08_09_000003_create_topic_tree_integrity_triggers.php` for the race an
application-level check cannot close. `App\Rules\SiblingSlugIsUnique` mirrors
the trigger so the common case becomes a friendly form error.

**Deletes block, they never cascade.** `App\Exceptions\DependentRecordsExistException`
is thrown from model `deleting` hooks and reports what depends on the record;
`restrictOnDelete()` backs it at the database level. This applies to topics with
children, education levels in use, images used as hero or branding, and media
files that are embedded or offered as downloads.

## 5. Routing and the content tree

`routes/web.php` registers a `/{path}` catch-all **last**, so every specific
route wins first. `App\Support\ContentPathResolver` walks the segments; a path
that does not resolve falls back to `slug_redirects` before 404ing.

Renaming a title never changes a slug. Changing a slug — or moving a node —
writes 301 redirects for the whole affected subtree via
`App\Support\SlugRedirectRecorder`, wired through `TopicObserver` and
`PageObserver`'s `updating` hook. The redirect target is a polymorphic
reference rather than a frozen path, so it stays correct through later renames.
**Callers must wrap the triggering `update()` in `DB::transaction()`** — see the
recorder's doc block.

Hidden topics and pages are excluded from navigation, the homepage grid,
listings and search, but still resolve at their direct URL. Hidden is
discoverability, not secrecy.

### Crawlers

`App\Http\Controllers\SitemapController` generates **both** `/robots.txt` and
`/sitemap.xml`. Neither is a file: the `Sitemap:` line needs an absolute URL and
behind the tunnel the domain is whatever Cloudflare forwards, so `public/robots.txt`
was removed and the two are produced together from the request.

The sitemap lists the homepage plus every topic and page that is not hidden,
has no hidden ancestor, and has no effective access password.

> **It deliberately does not consult the request.** Elsewhere, readability is a
> question about a visitor — `AccessControl::allows()` waves the admin through
> and honours unlock cookies. A sitemap is a public document that anything may
> fetch, cache and pass on, so it asks the visitor-independent question
> (`effectivePasswordId() === null`). Calling `allows()` here would write every
> protected path into the file whenever the owner loaded it while logged in.
> `SitemapTest` asserts the admin and an unlocked visitor both receive the
> byte-identical anonymous sitemap.

nginx has an exact-match `location = /robots.txt` to keep crawler noise out of
the access log. **It carries its own `try_files`** — an exact-match location
does not inherit one from `location /`, and without it the route 404s through
nginx while the whole suite passes.

### Ordering

`sort_order` is set by dragging, on `/admin/topics` (root topics, each topic's
subtopics, each topic's pages) and `/admin/levels`. The edit forms no longer
carry a number field.

`App\Support\SortOrder::apply()` is the single writer, behind
`topics.reorder`, `pages.reorder` and `levels.reorder`. It **reorders and never
reparents**: it refuses any request whose records do not already share the
grouping column (`parent_id` for topics, `topic_id` for pages; levels are flat
and pass `null`). Reparenting stays in the edit form because a move has to
carry the depth cap, cross-table sibling-slug uniqueness and the 301 redirects
a changed path leaves behind — none of which a drag would trigger. It writes
with `saveQuietly()` inside a transaction, so no observer fires and a reorder
leaves no redirects behind.

Because the field is absent from the forms, the requests infer it: `Store*`
puts a new record at the end of its own group, and `Update*` **keeps the
current value**, except when the parent changed, where the record joins the end
of its new group. Defaulting it to 0 there would throw the dragged order away
on every unrelated save.

`resources/js/components/admin/sortable-list.tsx` wraps `@dnd-kit`. The drag
handle is a real button with an accessible name, and the keyboard sensor is not
optional — every admin screen is operable without a mouse. Reordering posts and
re-renders from the server response; there is no optimistic client-side copy of
the tree.

### Duplicating a page

`POST admin/pages/{page}/duplicate` → `App\Actions\DuplicatePage`, which copies
the row, the body, the downloads and their level pivots in one transaction, and
redirects to the copy's edit screen.

What it does **not** copy is the interesting part:

| Not copied | Why |
|---|---|
| `downloads_count` | The tally belongs to the attachment that earned it. |
| `is_hidden` | Forced to `true`. A duplicate is identical to a live page until edited. |
| `slug_redirects` | A copy is a new page, not a page that moved. |

The body goes through `Page::writeContent()` rather than being assigned to the
column, so `content_text` is re-derived and `page_media_references` is rebuilt
for the copy — those rows are what make the files in the body reachable through
it. The slug is `-kopie`, then `-kopie-2` upward, checked against **both**
`topics` and `pages` because sibling uniqueness spans them and the Postgres
trigger turns a wrong guess into an exception.

## 6. Page content

TipTap v3, storing **JSON, never HTML**.

`App\Support\PageContent` is the server-side whitelist: an allow-list of node
types, per-node attributes and marks. Anything else is dropped. Link `href` is
restricted to http/https/mailto/relative — `javascript:`, `data:` and
protocol-relative are refused (the text survives; only the link mark is
dropped). This is what makes "store JSON" actually eliminate stored XSS: the
document comes from the browser, so constraining it server-side is the entire
point.

> **A node type added to the editor must be added here too, or it silently
> stops saving.** That is the safe direction to fail.

The whitelist covers paragraphs, three heading levels, both list kinds,
blockquote, hard breaks, the three embed blocks, **tables** (`table`,
`tableRow`, `tableHeader`, `tableCell`), and the marks bold, italic,
**subscript**, **superscript** and link. Paragraphs and headings may carry
`textAlign`.

Two attributes are listed in `NULLABLE_ATTRS`, and the distinction matters:
TipTap writes an explicit `null` for a paragraph nobody aligned and a column
nobody resized. Everywhere else in `sanitiseAttrs()` a null result means the
node is malformed and gets dropped; for `textAlign` and `colwidth` it means
there is no value, so the key is dropped and the node survives. Without that,
every table cell was rejected. A bad `colspan`/`rowspan` falls back to `1`
rather than rejecting — a merged cell drawn unmerged is cosmetic, a missing
cell is a hole in the table.

> **The `@tiptap/*` packages must be upgraded as a set.** v3 pins its peers to
> an *exact* version, so adding one package at a caret range pulls in a newer
> `@tiptap/pm` than the rest of the set allows and npm refuses to resolve. If
> the lockfile has already pinned the old versions, npm treats them as
> immovable — strip the `@tiptap` entries from `package-lock.json` and
> reinstall rather than fighting it with `--legacy-peer-deps`.

`Page::writeContent()` is the only writer. In one transaction it sanitises the
document, derives `content_text` (never client-supplied — it must describe what
is actually stored) and rebuilds the page's `page_media_references`.

`PageContent::sanitiseWithoutEmbeds()` additionally strips `fileEmbed`,
`youtubeEmbed` and `imageGallery`. Two bodies use it: the homepage
introduction (see [§10](#10-settings-and-branding)) and a topic's.

### Topic introductions

`topics.content` holds the same kind of document, written only by
`Topic::writeContent()` and rendered above the grid of children. It is edited
in the ordinary topic form, which carries the document on the `<Form>`'s
`transform` rather than in a hidden input.

Three things differ from a page body, each deliberately:

- **No embeds**, for the reason above: a file is published by walking from it
  to the *pages* showing it, and a topic is not a page row. An embed here
  would render for the owner and 403 for every student.
- **No `content_text` twin.** That column exists to feed
  `pages.search_vector`, and topics do not enter search results. Adding them
  means a column, a trigger and a product decision, together.
- **`content` is absent from `Topic`'s `#[Fillable]`**, so no future
  `update($request->validated())` can put an unwhitelisted document in the
  column by adding one validation rule. The form requests validate its
  *shape* only — enough to turn malformed input into a validation error
  rather than a TypeError — and the value is discarded on the way through
  `create()`/`update()`.

Access is inherited, not re-implemented: `ContentController::show()` runs the
password check before it decides whether to render a topic at all, so a locked
topic's introduction is never in the payload.

The renderer `resources/js/components/content/rich-text.tsx` maps node types to
React components and **never** uses `dangerouslySetInnerHTML` or TipTap's
`generateHTML`/`getHTML`. The single sanctioned exception in the tree is
Fortify's server-generated 2FA QR SVG in `two-factor-setup-modal.tsx`.

## 7. Media: storage, upload, serving

Two libraries — `images` (alt text required) and `media_files`
(`document` | `video`). Both are addressed publicly **by ULID, never by id**,
so the library cannot be enumerated.

### Upload

`App\Services\MediaLibrary` owns the flow. The **server** picks the chunk size,
the storage path (ULID + extension derived from the *resolved* MIME) and the
final type; the owner's filename is kept only as a display label and as the
download name. Type resolution prefers content sniffing and falls back to the
filename when sniffing is ambiguous (a `.docx` really is a zip) — the uploader
is the trusted site owner, so ambiguity resolves in favour of intent.

Chunks are ~20 MB because **Cloudflare Free/Pro rejects request bodies over
100 MB**. Raising PHP or nginx limits does not help.

`ingest()` registers a file already on disk and is shared by the chunked upload
(which has just assembled one) and by `media:import`.

### Images: conversion and compression

`App\Services\ImageOptimiser` runs inside `ingest()`, so both entry points get
it. **Every raster image becomes WebP.** The first reason is not size: a photo
off any recent iPhone is HEIC, which no browser renders, so storing it as it
arrived produces a broken image on the public page and nothing in the admin
screen would say so.

This needs ImageMagick's coders, which are separate Alpine packages —
`imagemagick-heic` and `imagemagick-webp` in the Dockerfile, plus the `imagick`
extension. GD cannot read HEIC at all. `ImageOptimisationTest` carries a
tripwire asserting both formats are registered.

The rules, in order:

1. SVG passes through — it is vector, and rasterising would be a downgrade.
2. An animated GIF passes through — flattening it to one frame destroys it
   silently, the worst way for a conversion to fail.
3. EXIF orientation is **applied and then** metadata stripped. A phone records
   orientation rather than rotating pixels, so stripping first puts every
   portrait photo on its side. Losing the rest is a privacy gain the site wants
   anyway: phone photos carry GPS coordinates.
4. The long edge is capped at `media.images.max_dimension`; nothing is enlarged.
5. Quality steps down from `quality` toward `min_quality` until the file is
   under `media.images.max_bytes`, then the dimension cap tightens and quality
   resets — ten points of WebP quality is far less visible than 40% of the
   pixels.
6. A re-encode that comes out **larger** is discarded and the original kept: a
   small PNG of flat colour grows as WebP.

Failure is judged by what a browser can do with the original. A JPEG that will
not re-encode is still a good JPEG and is kept; a HEIC that will not decode is
useless to every visitor, so the upload is refused. Nothing that can never be
displayed is ever stored.

`original_filename` has its extension corrected (`foto.HEIC` → `foto.webp`) —
it is the name a download saves under.

**`php artisan media:optimise`** reaches what ingest cannot: images that were
already in the library. It reports and writes nothing without `--force`, and
keeps each ULID, because that is what every embed, download and banner points
at — only the stored path's extension and the recorded MIME move.

### Uploading from the page editor

`components/admin/media-uploader.tsx` is the one upload client, used on the
media screen, in the downloads section of the page editor and inside the two
embed pickers. Two props carry the difference:

- `onUploaded(record)` — called per finished file and **awaited** before the
  next one starts. Providing it also suppresses the `router.reload()` the media
  screen relies on: a reload in the editor would throw away an unsaved body.
  The await is not cosmetic. Linking is an Inertia visit, and Inertia cancels
  the visit in flight when a new one starts, so parallel links would silently
  drop all but the last file.
- `compact` — the one-row drop zone, for use inside a section or a dialog.

`UploadController::complete()` answers with everything needed to use the file
without a reload: `type` (`image` | `file`), the numeric `id`, the ULID and the
display fields, keyed to match what `PageController::edit` already sends. The
type comes from sniffing the assembled bytes, so **the client only finds out
here** — an image uploaded in the downloads section says so rather than
failing. The numeric id is not a break with "address media by ULID": this
endpoint is behind `auth`, attaching a download is a relational write keyed on
it, and public routes still resolve media by ULID only.

Where an upload lands:

| From | Result |
|---|---|
| Media screen | Library only. |
| Downloads section | Library **and** attached to this page, with the levels ticked above the drop zone. |
| File picker | Library **and** inserted into the body at the cursor. |
| Image picker | Library, and ticked in the selection — the gallery is a batch, so nothing is inserted until *Invoegen*. |

A download attached without a `sort_order` joins the end of the page's list
(`StorePageDownloadRequest`). A batch of uploads attaches faster than the
editor's copy of the list refreshes, so the client cannot count; the server is
the only one that sees them in sequence.

The editor's media library can now grow while the editor is open, which the
extension options were not built for: `useEditor` builds the extension list
once and the node views keep whatever object they were handed, so replacing it
would mean recreating the editor and losing the caret and undo history.
`GrowingEditorLibrary` (in `components/editor/media-library.ts`) is that one
object — the node views hold it for the editor's life while its arrays are
swapped, and a parallel React state copy re-renders the picker dialogs.

### Picking: three endpoints, none of them a library

No screen receives the media library any more. Each picker is handed only what
the thing being edited already points at, and searches for the rest:

| Endpoint | Addresses by | Feeds |
|---|---|---|
| `GET /admin/media/search/images` | ULID | the editor's image picker |
| `GET /admin/media/search/files` | ULID (+ an `exclude` id list) | the file picker and the downloads dialog |
| `GET /admin/media/search/image-options` | numeric id | the page banner and the three branding pickers |

All three live on `Admin\MediaSearchController`, behind `auth`, capped at 50
rows, matching with `ILIKE` on filename and — for images — alt text. This is
metadata, never bytes: `MediaAccess` gains no caller.

The last row is a separate endpoint rather than an extra field on the first,
and that separation is the point. The editor writes a ULID into a document; a
banner and the branding settings write a foreign key. Handing the editor's
picker an id it does not need is how that distinction quietly stops being
true. `Image::toPickerOption()` is the single definition of the id-addressed
shape, because three controllers send it and the search endpoint has to match.

Every `q` and the `exclude` list are `nullable`, which is load-bearing: a
picker fetches once when its dialog opens, before anything is typed, so the
browser sends `?q=` and `ConvertEmptyStringsToNull` makes that null.
`['sometimes', 'string']` then refuses it — `sometimes` does not help, the key
is present and only its value is empty — and the dialog draws an empty grid
with no explanation until a character is typed.

### Serving

Deciding and streaming are deliberately separate:

- `App\Support\MediaAccess` **decides**. Single decision point, fail-closed.
- `App\Support\MediaStream` **emits** an `X-Accel-Redirect` into the `internal`
  `/__media/` location, which nginx streams with native Range support.

Two routes stream media — `MediaController` (by ULID) and `DownloadController`
(a page's download, which also keeps the tally). Both authorise through
`MediaAccess` first. The invariant is that single decision, not any one
controller being the only door: a third caller is fine, a second copy of the
streaming code is not.

`MediaStream` refuses any stored path outside the two library directories — the
nginx alias points at the private disk root, so a bad `path` column would
otherwise be served verbatim.

`MEDIA_X_ACCEL=false` makes PHP stream instead. That exists for the test suite
and `artisan serve` only. **Authorisation runs before that branch**, so the two
paths cannot disagree.

The private disk sets explicit `permissions` in `config/filesystems.php` so
nginx — a different user, read-only mount — can read what PHP-FPM wrote. Chunk
staging is chmodded back to `0700`; nginx has no business reading
half-assembled uploads.

`'serve' => false` on the `local` disk must stay false. `serve => true`
registers framework GET/PUT routes at `/storage/{path}` that read and write
that disk behind nothing but a signed URL, and would make
`Storage::temporaryUrl()` mint shareable links that skip `MediaAccess`
entirely. `MediaAccessTest` asserts both routes stay absent.

## 8. Access control

### Pages

`App\Support\AccessControl` resolves a page's effective password: **nearest
ancestor wins**, so a page inside a protected branch can carry its own password
without the branch's leaking into it. Resolution is deliberately **uncached** —
a stale answer here is a disclosure bug, not a slow page. If it ever matters,
denormalise into a trigger-maintained column; do not add a static cache.

The unlock cookie carries a **fingerprint of the current hash**, not just the
record id, so changing a password invalidates every cookie issued under the old
one. That is the only revocation mechanism, and the reason
`AccessPassword::changePassword()` exists rather than a plain `update()`.

The prompt **replaces** the content server-side (`content/locked`); no part of
a locked body is ever sent. Unlock is `POST /unlock` taking the **path**, never
a password id, so the form cannot be used to probe which password guards what.
Rate limited per IP per password (`config/access.php`), which depends on
`trustProxies(at: '*')` in `bootstrap/app.php`.

Password **names are shown to visitors**, so someone holding two passwords
knows which is being asked for.

### Media

`MediaAccess::allows()`:

1. Authenticated → allow. There is exactly one account, it cannot be deleted,
   and registration does not exist, so authentication is sufficient — the owner
   must be able to preview everything, including files not yet on a page.
2. Otherwise `isPubliclyReachable()`, which allows a file when:
   - it is currently referenced by a **branding setting** (logo, favicon,
     homepage banner) — the one category not reached through a page at all; or
   - **some page showing it** is one this visitor may open.

"Showing it" means: embedded in a body (`page_media_references`), offered as a
download (`page_downloads`), or — for images — used as a page's
`hero_image_id`. The hero deliberately resolves through the same page walk
rather than getting a case of its own, so it inherits the page's password.

Any reachable page is enough. A worksheet published on an open revision page is
public even if it also appears on a protected class page: refusing it via one
URL while serving it via another protects nothing. **Passwords guard pages, not
files.**

Hidden pages count as reachable, for the same reason they still render at their
direct URL.

Downloads and body embeds are checked **separately** on purpose:
`page_media_references` is derived data rebuilt wholesale on every body save, so
a download folded in there would be deleted the next time the body was edited.

## 9. Search

`pages.search_vector` is a `tsvector` maintained by a **database trigger**,
weighted A/B/C over title, description and `content_text`, with a GIN index.
`content_text` is already derived; a second derivation in PHP would be one more
thing that can drift.

### Which language the corpus is stemmed in

The configuration is not named in the trigger. It comes from a `STABLE` SQL
function, `content_search_config()`, which reads the `content_language` setting
and falls back to `dutch`:

```sql
create or replace function content_search_config() returns regconfig as $$
    select coalesce(
        (select cfgname::regconfig
           from pg_ts_config
          where cfgname = (select value #>> '{}' from settings
                            where key = 'content_language')),
        'dutch'::regconfig);
$$ language sql stable;
```

Three things about that are deliberate:

- **It is looked up in `pg_ts_config`, not cast.** A direct
  `value::regconfig` turns one wrong settings row into an exception on **every
  page save**. The value arrives from a form, through `jsonb`, from a table;
  falling back is the only acceptable failure.
- **`STABLE`, so the planner may call it once per statement** rather than once
  per row. It is one extra `SELECT` on a write performed by one person a few
  times a day.
- **This is the owner's writing language, not the visitor's interface locale.**
  They are different questions. `search_vector` is one stored column, stemmed
  once when the page is saved; re-stemming per visitor is not something
  Postgres can do, and it would be the wrong answer anyway — a Dutch worksheet
  is still Dutch when an English-reading visitor searches for it. See
  `App\Support\ContentLanguage`, which owns the allow-list
  (`dutch`, `english`) and is the only thing that decides what the settings
  screen offers.

`SearchController` calls `content_search_config()` too, in all three places it
needs a configuration. A query parsed with a different stemmer than the index
was built with silently fails to match pages that plainly contain the word, so
the two read the same function rather than agreeing by convention.

**Changing the setting re-indexes synchronously.** The trigger only fires on a
write, so pages already stored keep their old stemming — the setting appears to
take effect and search quietly keeps missing words.
`SiteSettingsController::update()` runs `php artisan search:reindex` when the
value changed; the command is `update pages set title = title`, the migration's
own backfill idiom, which touches a column the trigger watches. No queue and no
chunking: the corpus is tens to hundreds of rows, and one statement means a
failure leaves the old index intact rather than half of a new one.

Queries use **`websearch_to_tsquery`**, not `to_tsquery`: it parses what people
actually type (quoted phrases, `-word`) and never throws on punctuation. That
is load-bearing — the input is a public search box.

Results exclude hidden pages always, and protected pages unless the visitor has
unlocked them; a title and snippet would leak precisely what the password
withholds. Access filtering happens in PHP after an over-fetch, because
readability depends on cookies and on walking the tree.

`ts_headline` runs with `StartSel`/`StopSel` emptied: snippets are rendered as
text, never markup.

## 10. Settings and branding

`settings` holds **overrides**; `App\Support\SiteSettings::DEFAULTS` owns the
defaults. An empty table therefore renders correctly, and resetting a setting is
a delete rather than a guess at what it used to say. Deliberately uncached, for
the same reason `AccessControl` is.

Image settings store an `images.id`. `SiteSettings::all()` **normalises them to
`int`** — they arrive from an HTML form as `"7"`, and every reader compares
strictly (`in_array(..., true)` in `MediaAccess`, `===` in the React picker).

The site title and favicon are rendered by `resources/views/app.blade.php`
through a view composer registered in `AppServiceProvider::shareBranding()`,
not from React: they must be right before hydration or the tab flickers from
the default name on every first load. `resources/js/app.tsx` reads
`<meta name="app-name">` for the title template so client-side navigations
agree with the server. `HandleInertiaRequests::share()` additionally exposes
`branding` (title, logo, favicon) to every page.

**The homepage introduction cannot contain embeds.** Embeds publish a file by
walking from it to the *pages* showing it, and the homepage is not a page row —
an embed would render for the owner and 403 for everyone else.
`SiteSettingsController::update()` runs the document through
`PageContent::sanitiseWithoutEmbeds()`;
`resources/js/components/editor/simple-text-editor.tsx` simply does not offer
the buttons.

The top-level category grid always renders and cannot be edited away.

## 11. Authentication

- **No registration.** `Features::registration()` is removed from
  `config/fortify.php`; there is no register route, action or page.
- **The admin account cannot be deleted.** No route, no controller action, and
  a `deleting` guard on `User` that throws.
- **No `verified` middleware anywhere.** E-mail verification is disabled, so the
  only account never has a `verified_at`; gating on it would lock the owner out.
- **First-run claim** at `/admin/claim`, gated by `guest` + `admin.unclaimed`.
  The exists-check-and-insert is atomic via a PostgreSQL advisory lock in
  `App\Support\AdminAccount::claim()` — see its doc block for why a plain
  transaction is not enough.
- `FortifyServiceProvider`'s `loginView` closure redirects on to the claim
  screen while unclaimed, so future admin routes inherit the gate for free by
  living behind `auth`.
- Optional `ADMIN_SETUP_TOKEN` (`App\Support\AdminSetupToken`, constant-time
  compare) closes the first-come-first-served claim window.
- Recovery is `php artisan admin:reset-password`, interactive only. There is
  deliberately no `--password` flag.
- Rate limiters: Fortify's `login`, plus `claim` and `uploads` in
  `AppServiceProvider`.

## 12. Frontend conventions

- **Do not wrap a page in `AppLayout` yourself.** `resources/js/app.tsx`
  resolves the layout by page name. A page that also renders one gets **two
  sidebars** and a content column squeezed to a third of its width — invisible
  at 1280 px, clipping controls at 768 px. Set
  `Component.layout = { breadcrumbs: [...] }` like every other admin screen.
- Public pages (`welcome`, `content/*`) resolve to `null` and wrap themselves in
  `PublicLayout`; they must never inherit the admin shell. `PublicLayout`
  carries the search field and, **only for an authenticated visitor**, a
  *Beheer* link. There is no login link on the public site: students never log
  in, so the owner reaches `/login` by typing it.
- `DashboardController` renders the admin landing page. Its `nextSteps` array
  is the closest thing this application has to a setup wizard — a checklist
  that hides itself once every step is done. It is read-only; every action it
  suggests happens on the screen it links to.
- Flash messages (`session('status')` / `session('error')`) are shared globally
  by `HandleInertiaRequests::share()`, not passed per controller.
- Forms use Inertia's `<Form {...action.form()}>` with Wayfinder helpers.
- **`$request->validated()` returns only keys that have rules.** Validating
  `content.type` and then reading `validated()['content']` silently erases the
  whole document. Both `PageController::updateContent()` and
  `SiteSettingsController::update()` validate the shape and then read
  `$request->input(...)`.
### Interface language

Two locales, `nl` (the default) and `en`. **Only the interface is translated.**
Everything the owner writes — page and topic titles, descriptions, download
labels, education-level names, the site's own name, the homepage copy — is
content and is stored once, in whichever language it was written in. Which
language the *corpus* is stemmed in is a separate setting; see §9.

- **`App\Support\Locale`** owns the supported set, the default and the cookie
  name, and resolves a request: a validated `locale` cookie, else
  `Accept-Language` negotiated against the set, else `nl`. Validated against
  the enum for the same reason `HandleAppearance` validates — the value reaches
  a Blade `<script>`, which is the wrong escaping context for `{{ }}`.
- **`App\Http\Middleware\SetLocale`** applies it (`app()->setLocale()`,
  `CarbonImmutable::setLocale()`) and shares the active dictionary to the view.
  Registered in `bootstrap/app.php` **before** `HandleInertiaRequests`.
- **`POST /taal`** (`LocaleController`) sets the cookie and redirects back. The
  cookie is server-set, so it stays encrypted and needs no entry in
  `encryptCookies(except:)` — strictly better than the `appearance` cookie,
  which JS writes.
- **Switching is a full page load**, not an Inertia visit. `<html lang>` and
  the document title are server-rendered.

**The dictionary is a Blade global, not an Inertia shared prop**, and that is
deliberate. `resources/views/app.blade.php` emits `window.__translations` and
`window.__locale` next to the existing first-paint appearance script. It ships
**once per document** rather than on every Inertia visit, and it is right
before hydration rather than after it. SSR is not enabled, so a boot-time
global is safe.

**Only `common` and `ui` reach the browser.** `Locale::dictionary()` filters on
an allow-list (`CLIENT_GROUPS`), not a deny-list, so a group added for the
server — `validation`, `admin`, `backup` — can never start riding along on
every document by accident.

`resources/js/lib/i18n.ts` is about forty lines: `t(key, params)` with `:name`
interpolation and Laravel's `singular|plural` choice form selected on
`params.count`, plus `intlLocale` (`nl-NL` / `en-GB`) for everything that
formats a date or a number. **No i18next, no react-intl** — a library would add
a second message format, a second place to register a locale, and a bundle, for
a lookup and a two-form plural.

Two traps worth knowing:

- **A module-scope constant freezes the language.** The dictionary is set per
  document, so `const LABELS = { done: 'Klaar' }` at import time keeps whichever
  language happened to load first. The uploader's status labels and the file
  library's kind labels hold *keys* and resolve at render for exactly this
  reason.
- **A key built from a variable cannot be checked.** `LocalisationTest` scans
  for literal `t('…')` and `__('…')`, so the few places that interpolate — the
  dashboard's steps, `IconCatalogue`'s library labels, the locale switcher's
  options — build the key from a fixed list.

`tests/Feature/LocalisationTest.php` is the whole guard, since there is no JS
test runner here: identical file sets, identical key sets compared recursively,
no message identical in both locales (with an explicit allow-list, because
Dutch borrowed most of the computing vocabulary wholesale), and every key the
application asks for present in every locale. Comments are stripped before the
scan — `lib/i18n.ts` documents itself with three example calls.

**Artisan output stays English.** It is an operator surface, like the code and
the commit messages. So are the two developer-facing documents; the three
end-user guides each exist in both languages — deployment/installatiegids,
maintenance/onderhoud-en-beveiliging and administration/beheerdersgids — kept
in step by hand, deliberately, the same as the language split it documents.

### Icons

About 15,000 icons from four sets: lucide (ISC), tabler and tabler-filled
(MIT), and Material Design Icons (Apache-2.0). Licences: `database/data/LICENCES.md`.

- `scripts/build-icon-catalogue.mjs` (`npm run icons:build`) reads each
  package's **own exported geometry** and writes `database/data/icons.json`.
  **Never a hand-written list** — in v1 a hand-curated list produced blank
  tiles because names were guessed. The file is committed, because PHP cannot
  regenerate it and a deploy that failed to build it would silently lose every
  icon on the site.
- `php artisan icons:sync` loads it into the `icons` table. It runs from the
  entrypoint on every boot and is a no-op when a checksum matches.
- `App\Support\IconCatalogue` is the only lookup point. Controllers send
  geometry for **only the icons their page draws**; `components/icon.tsx`
  turns the stored `[tag, attributes]` nodes into React elements. Nothing is
  injected as HTML, and the browser downloads no icon catalogue at all.
- Stored values are `library:name`. **An unprefixed value means lucide**, which
  is what keeps icons chosen before the catalogue existed working without a
  migration.
- The picker searches server-side at `GET /admin/icons` (behind `auth`).
- Tabler and MDI are devDependencies. If you update them, re-run
  `npm run icons:build` — nothing warns you that the catalogue has gone stale.

## 13. Design system

**All colour lives in `resources/css/app.css`.** The raw palette sits in one
block at the top; every semantic role points at it. To rebrand, edit that block
only. Never hard-code a colour in a component.

Two rules that are load-bearing rather than stylistic:

- **A fill role and a text role cannot be the same token.** A mid-luminance
  colour fails one way or the other. `destructive` is a fill with
  `destructive-foreground` on it; `error` is the text role. Green and yellow are
  fills with dark text and are never used as text colour on light backgrounds.
- **Anything used as text must clear AA on `--card`, not just on the page
  background.** In the dark theme the card is *lighter*, so it is the harder
  case.

White text on the brand blue is 3.2:1 and fails AA, which is why primary
buttons carry dark navy labels.

**Measure contrast by setting `localStorage.appearance` and reloading, never by
toggling `.dark` on a live page.** Components carry
`transition-[color,box-shadow]`, so `getComputedStyle().color` during a live
toggle returns a mid-animation value — that produced a page of confident,
entirely fictional failures before the cause was found.

## 14. Testing

PHPUnit-style feature tests under `tests/Feature`, against **real PostgreSQL** —
the schema needs tsvector, GIN and CHECK constraints, so SQLite is not an
option.

```bash
docker compose -f compose.yaml -f compose.dev.yaml exec app php artisan test
```

`tests/bootstrap.php` forces the test environment across `$_SERVER`, `$_ENV` and
`putenv()`. Compose injects `.env` into the real environment and Dotenv reads
`$_SERVER` first, so `<env force="true">` in `phpunit.xml` is not enough on its
own. Without the bootstrap, CSRF stays on (419 on every POST) and
`RefreshDatabase` truncates the **development** database. `TestCase::setUp()`
independently refuses any database whose name does not end in `_testing`.

> **The suite cannot catch nginx-side breakage of gated media.** Tests run with
> `MEDIA_X_ACCEL=false`, so PHP reads the file itself, as the same user that
> wrote it. Production hands the path to nginx, which reads it as a *different*
> user from a read-only mount. That difference already caused one total outage
> that 127 green tests did not notice: the private disk's Flysystem default
> created directories `0700`, nginx could not traverse them, and every image,
> download and video 403'd. After touching disk config, the web image or the
> `/__media/` location, **fetch a real gated URL through nginx.**

### Browser tests

Playwright drives **Chromium against the real stack, through nginx**:

```bash
docker compose -f compose.yaml -f compose.dev.yaml exec app php artisan e2e:seed
docker compose -f compose.yaml -f compose.dev.yaml --profile e2e run --rm e2e
```

Specs live in `tests/e2e`, configuration in `playwright.config.ts`. The service
is behind a profile so an ordinary `up -d` never starts it, and it reaches the
site as `http://web` rather than a published port — the point is to go through
the same nginx that ships.

**There is deliberately no jsdom half.** The regressions that justified a
JavaScript runner at all were a drag landing on the wrong list, an iframe
missing an attribute, and a header nginx sets. jsdom has no layout engine, so
`getBoundingClientRect()` returns zeroes and dnd-kit's collision detection
degenerates — a test for the first would only ever assert against rectangles
the test itself had faked, which is precisely what it must not do. Vitest is a
fine tool; it cannot see the class of bug this exists for.

`php artisan e2e:seed` writes the fixtures the specs expect and is **not**
reached from `DatabaseSeeder`, which the entrypoint runs on every boot
including on the teacher's own install. It refuses outside development, because
it writes throwaway content and resets the admin password so the specs can log
in. It restores fixture state rather than merely declining to duplicate it: the
ordering specs reorder what they find, so a second run has to put it back.

Four things that are load-bearing and easy to undo:

- **The suite logs in once**, in a setup project that saves the session to
  `tests/e2e/.auth` for the others to reuse. Fortify allows five logins a
  minute per e-mail and IP and the whole run comes from one address, so a login
  per test sat exactly on the limit: a second run inside the same minute was
  throttled, and the refusal looked like an admin screen that would not load.
  The saved cookies are added to each page's own context rather than set as a
  project-wide `storageState`, because the `request` fixture is a separate
  context and the media specs need it genuinely anonymous.
- **The Playwright image tag must match `@playwright/test` in `package.json`.**
  Playwright refuses to drive browsers it did not ship with. `.npmrc` sets
  `ignore-scripts=true`, so npm never downloads a second copy — the ones in the
  image are the ones used, and only the tag keeps them in step.
- **`SESSION_SECURE_COOKIE` is `false` in the development overlay.** A browser
  will not store a `Secure` cookie over `http://` unless the origin is
  trustworthy, and only `localhost` qualifies. Reaching the site by service
  name drops the session silently and every login looks like a wrong password.
- **The suite runs single-worker.** One database, one site, and several specs
  reorder or attach things; parallel workers would race through the same
  fixtures and the failures would read as product bugs. There are no retries
  either — a test that passes on the second attempt is telling you something.

CI starts `web`, seeds, and runs the same command. On failure it uploads the
Playwright trace, which is a step-by-step recording with the DOM at each step;
a failed browser test is close to unreadable from a log alone.

### The production smoke test

```bash
./scripts/smoke-production.sh https://your-site.example
```

Both suites above run against the **development** target: root, from a bind
mount, with `MEDIA_X_ACCEL=false`. Production is www-data, from a baked image,
with named volumes and nginx doing the streaming. That gap is a category of
bug neither suite can see, and it has already caused an outage — a directory
missing from the image became a root-owned mount point the application could
never write to, while every test stayed green.

So this script asks what only a production boot can answer, and asserts rather
than prints: the container is unprivileged, opcache is in its production
configuration, every named-volume mount point is writable by the user that
must write to it, a backup archive is produced and is a valid gzip, the built
assets are in the image, debug output is off, the security headers survive in
every location that sets one of its own, the internal locations are
unreachable, `robots.txt` and `sitemap.xml` are generated with an absolute
URL, and a gated download streams from nginx with an ETag and working ranges.

It reads `SMOKE_PROJECT` for the compose project to inspect (default
`teacher`) and takes the base URL as its first argument. It is safe against a
live site: it writes one archive and removes it, and otherwise only reads.

The gated-media check discovers a file through the site's own sitemap, because
a production image has no tinker to ask the database with. On a site whose
content is entirely hidden it finds nothing and says so; pass
`SMOKE_MEDIA_URL=/downloads/…` to point it at one.

> Only wrong **ownership** reproduces that outage. Laravel's local adapter
> re-applies the configured directory permissions, so a wrong mode heals
> itself on the next write — which also means a `chmod`-based test of this
> proves less than it appears to.

## 15. Backup and restore

`App\Services\BackupArchive` builds and applies one `.tar.gz` that is enough to
stand the site up somewhere else. Its layout is flat and boring:

```
manifest.json      format version, timestamp, last migration, row counts
database.sql       pg_dump --clean --if-exists, plain SQL
images/ media/     the private disk, verbatim
```

**Both halves or neither.** A database dump without the media restores into a
site whose every image and download is a dead link — worse than an obvious
failure, because it looks like it worked.

Plain SQL rather than pg_dump's custom format: it restores with `psql` alone, a
human can read and repair it when something has gone wrong, and it is not tied
to one `pg_restore` version. The whole thing is gzipped, so the text costs
little.

### What is deliberately not in it

- **`.env`.** It holds the database password and `APP_KEY`, and an archive is a
  file the owner is encouraged to copy onto a laptop and a USB stick. Leaking
  the key alongside a full database dump is a different category of accident
  from losing it. The install guide says to keep `.env` separately.
- **Chunk staging.** Half-finished uploads are worth nothing to a restore and
  can be enormous.
- **The code.** It comes from the repository.

### Where archives live, and why not on the media disk

Their own disk (`backups` in `config/filesystems.php`) on their own Docker
volume. Two reasons, and both bite:

- the media volume is one of the things an archive *contains*, so archives kept
  inside it would make every backup contain the previous ones;
- `MediaStream` aliases the private disk root and serves anything under the two
  library directories. An archive holds the whole database, the admin password
  hash included.

### Serving one

Same mechanism as gated media, a **different** decision. nginx streams from an
`internal` location — but `/__backup/`, not `/__media/`, mounted `:ro` on the
web container. `MediaStream::send()` and `sendArchive()` share one private
`emit()` so there is a single copy of the X-Accel logic; what they do *not*
share is the authorisation.

`BackupController` never consults `MediaAccess`. That class answers "may this
visitor see this file", and its answer is yes for anything a public page shows
— exactly the wrong question. The right one is "is this the owner", which the
`auth` middleware already answered. Everything else about an archive follows
from that: `BackupArchive::resolve()` accepts only
`teacher-backup-\d{4}-\d{2}-\d{2}-\d{6}\.tar\.gz`, filenames only, no
directories and no traversal.

### Restoring

`backup:restore` replaces the database and both media directories. Media is
replaced **wholesale, not merged**: a file the archive does not contain is a
file the restored database knows nothing about, and leaving it behind would
quietly keep an old site's uploads on the new machine. There is no merge mode
at all — reconciling two sites' content needs decisions a command line cannot
ask for.

The manifest's `format` is checked first. An archive from a newer version is
refused with an explanation rather than half-applied; a partly-restored site is
worse than one that never started. A non-interactive run without `--force`
refuses too — this is the one command in the project that can destroy
everything.

`restore.sh` wraps it for an operator: safety archive, `docker cp` in,
`backup:restore --force`, restart, health check. `install.sh` calls the same
script when `TEACHER_RESTORE=` is set, which is how a site moves machine —
install, restore, done. The admin account comes back with the database, so
there is no claim screen to race and no setup token to find, and the installer
suppresses the claim instructions in its summary when it restored.

### Retention

Nothing is deleted unless asked. `backup:run --prune` keeps `BACKUP_KEEP`
(default 7); `--keep=N` overrides it for one run. A nightly cron line that
silently discarded the only copy of a year's work because a default said seven
is not a trade this application makes — hence the flag, and hence the
maintenance guide putting the schedule on the host where the operator can see
it rather than in Laravel's scheduler, which nothing in this stack runs.

### `pg_dump` and `tar` live in the image

`postgresql17-client` and `tar` are installed in the Dockerfile's base stage.
The client major version must match the server: `pg_dump` refuses a server
newer than itself.

`writeArchive()` streams the media directories in place with repeated `-C`
rather than copying them first — a media volume is routinely larger than the
free space needed to duplicate it. Secrets reach `pg_dump` and `psql` through
`PGPASSWORD` in the environment, never argv, the same rule `install.sh`
follows.

## 17. Where the bodies are buried

Short list of things that have already cost time. Each one has the long-form
reasoning in a comment where it bites.

- The entrypoint is in the image — **rebuild**, do not restart.
- Named volumes mount root-owned; the entrypoint chowns `storage` and
  `bootstrap/cache` when running as root.
- `vite.config.ts` needs `server.origin` **and** `server.cors`, together, and a
  service restart.
- `$request->validated()` drops unruled keys, which silently erases rich-text
  bodies.
- Image ids from HTML forms are strings; `SiteSettings::all()` casts them.
- Do not render a layout inside a page component.
- Do not toggle `.dark` on a live page when measuring colour.
- `DatabaseSeeder` deliberately creates no user. The starter kit's
  `test@example.com` would occupy the single admin slot on a live deploy.
- A YouTube iframe must carry `YOUTUBE_REFERRER_POLICY`. The site-wide
  `Referrer-Policy: same-origin` sends no `Referer` cross-origin at all, and
  the player answers "error 153" rather than playing. Relax it on the iframe,
  never in nginx.
- The backup tests use `DatabaseTruncation`, not `RefreshDatabase`. The latter
  wraps each test in an open transaction; `pg_dump` connects separately and
  sees only committed data, so every archive would be of an empty database — a
  green test proving nothing — and `psql` would then deadlock dropping tables
  that transaction still locks.
- A picker's first search sends `?q=`, `ConvertEmptyStringsToNull` makes that
  null, and `['sometimes', 'string']` then refuses it — so every dialog opened
  onto an empty grid until a character was typed. Search parameters are
  `nullable`.
- nginx resolves `app` once, when it loads its configuration, and caches it for
  the life of the process. A `web` container with no `app` on the network
  refuses to start at all. `update.sh` force-recreates `web` after the stack is
  up for the same reason.
- `update.sh` replaces itself while bash is executing it. bash reads a script
  incrementally by byte offset, so the last line is `main "$@"; exit $?` — one
  line, parsed together, so nothing is ever read from the file again.
- An exact-match nginx `location =` does not inherit `try_files` from
  `location /`. That is why `/robots.txt` 404'd through nginx while the whole
  suite passed.
